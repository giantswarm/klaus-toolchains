# klaus-toolchains

Public toolchain container images in two families:

- `klaus-*`: images that extend the minimal [Klaus](https://github.com/giantswarm/klaus) base with language runtimes and tools, for klausctl.
- `harness-*`: kagent Harness images that extend the Giant Swarm kagent line's `claude-harness` image with a toolchain. Each runs as its own Harness, `claude-<toolchain>`.

## Images

Each image adds exactly what it needs on top of Klaus. Variant is encoded in the image name, not the tag.

| Image | Contents | Base |
|-------|----------|------|
| `giantswarm/klaus-toolchains/go` | + git, Go runtime | `giantswarm/klaus` |
| `giantswarm/klaus-toolchains/go-debian` | + git, Go runtime (Debian) | `giantswarm/klaus-debian` |
| `giantswarm/klaus-toolchains/harness-node` | + Node.js 24, npm, corepack (pnpm, yarn), python3, make, g++ | `giantswarm/kagent/claude-harness` |

### Image hierarchy

All toolchain images build directly from the Klaus base to avoid cross-image registry dependencies:

```
giantswarm/klaus
└── giantswarm/klaus-toolchains/go          (+ git + Go)

giantswarm/klaus-debian
└── giantswarm/klaus-toolchains/go-debian

giantswarm/kagent/claude-harness            (claude, kagent-claude, git, gh, glab)
└── giantswarm/klaus-toolchains/harness-node (+ Node.js; the claude-node Harness)
```

### Harness images

A `harness-<name>/` image is `FROM` the kagent line's `claude-harness` image, pinned by tag and digest. The toolchain layer never touches `/usr/local/bin/claude`, `/usr/local/bin/kagent-claude`, the `kagent` user (uid 65532), `/data` or the image's `USER` and `ENTRYPOINT`. Renovate re-bases every harness image on each kagent-line release in one PR, reviewed by Bumblebee (`renovate-custom.json5`), and Node.js within its major.

The `Harness contract` workflow (`.github/workflows/harness-contract.yaml`) builds every harness image on each pull request that touches one, Renovate's re-base among them, and runs `scripts/harness-contract.sh` against its base:

- `ENTRYPOINT` is `kagent-claude`; `ENTRYPOINT`, `CMD`, `USER` and `WORKDIR` are the base's;
- `claude` and `kagent-claude` are the base's files, so `claude --version` is the line's pin;
- the `kagent` user is 65532:65532 and the `/data` layout (`adapter`, `claude`, `generated`, `workspace`) is the base's;
- `git`, `gh` and `glab` answer `--version`;
- `kagent-claude --check` passes with `strict_version` on the pinned version;
- every line of `harness-<name>/contract-commands` answers as the `kagent` user.

Run it locally with `docker build -t harness-node:dev harness-node && scripts/harness-contract.sh harness-node harness-node:dev`.

Harness images are published to `gsoci.azurecr.io` only. The kagent chart renders one as a Harness of its own, pinned by digest (a tag is refused), through its `harnesses` values:

```yaml
harnesses:
  - name: claude-node
    runtime: claude
    displayName: Claude Code (Node.js)
    image: gsoci.azurecr.io/giantswarm/klaus-toolchains/harness-node@sha256:<digest>
    snapshotLocation: s3://<bucket>/<prefix>
```

## Tagging

Each image has its own independent version lifecycle. Tags use the format `<name>/v<semver>`:

- `go/v0.1.0`
- `harness-node/v0.1.0`

This format is required by `architect project version --git-tag-prefix` for correct version extraction in mono-repos.

On every push to `main`, the `Toolchain release` workflow (`.github/workflows/toolchain-release.yaml`) releases each `klaus-*/` and `harness-*/` directory that changed since its latest `<name>/v*` tag: the next patch tag (e.g. `go/v0.1.0` -> `go/v0.1.1`) and a GitHub Release. Tags are pushed one at a time so each starts its own CircleCI release pipeline, and the workflow triggers a pipeline through the CircleCI API if one never showed up. A failed run is caught up by the next push or by running the workflow by hand.

The workflow is not generated by devctl: devctl's Auto-release releases a repository as one un-prefixed `v*` line (giantswarm/devctl#2591 tracks a prefixed mode).

Dev builds on branches use commit-SHA-based tags automatically via `architect project version`.

## Build args

| Arg | Default | Description |
|-----|---------|-------------|
| `KLAUS_VERSION` | pinned | Klaus base image version. Updated by Renovate. |
| `GO_VERSION` | `1.25` | Go version (klaus-go only). Managed by platform team. |

Harness images take no build args: their bases are digest-pinned `FROM` lines that Renovate updates.

## Usage

Reference images in klausctl config, Helm values, or operator CRDs:

```yaml
image: gsoci.azurecr.io/giantswarm/klaus-toolchains/go:0.1.0
```

## Repository structure

```
klaus-go/
├── Dockerfile           # Alpine variant
└── Dockerfile.debian    # Debian variant
harness-node/

```

## CI

CircleCI uses [dynamic configuration](https://circleci.com/docs/dynamic-config/) to auto-discover images. A setup job runs `.circleci/generate-config.sh`, which:

- **Branch builds**: finds which `klaus-*/` and `harness-*/` directories changed vs `origin/main` and generates `push-to-registries-multiarch` jobs for those only (amd64, dev tags).
- **Tag builds**: parses the tag prefix (e.g. `go` from `go/v0.1.0`) and generates multi-arch release jobs for the matching image.
- **No changes**: emits a no-op workflow.

Harness images are pushed to `gsoci.azurecr.io` only, without the China mirror.

Adding a new image is as simple as creating a `klaus-<name>/` or `harness-<name>/` directory with a `Dockerfile` -- no CI config or Makefile edits required. Its first merge releases `<name>/v0.1.0` (`harness-<name>/v0.1.0`).
